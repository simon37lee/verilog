# mandelbrot

Mandelbrot 집합 실시간 렌더러. 320x240 프레임버퍼를 640x480 HDMI 로 2 배 확대해서 보여 주고
(v5 부터는 800x600 을 DDR2 프레임버퍼에 그려서 1:1 로),
왼쪽 위에 프레임 하나를 그리는 데 걸린 시간과 fps 를 표시한다. 코어 구조를 단계별로 바꿔 가며 이 숫자를 줄이는 것이 목표.

기본은 **자동 데모**: 렌더 프레임마다 Seahorse Valley (-0.7436, 0.1318) 쪽으로 중심을 당기며 1/32 씩 확대하고,
한계 (W = 18 이면 32 배, v4 의 W = 34 면 2^19 = 52 만 배) 에 닿으면 중심은 그대로 두고 처음 배율까지 축소하기를 반복한다. 움직임이 렌더 프레임 단위라서 코어가 빨라질수록
애니메이션이 빠르고 부드러워진다. 더블 버퍼 (버퍼 2 개, vsync 에 교체) 라서 화면이 찢어지지 않는다.

```
 clk_core (50 MHz)                                          clk_pix (25 MHz)
 버튼 ─► mandel_render ─► mandel_core ─► 프레임버퍼 BRAM ─► mandel_display ─► TMDS ─► HDMI
         (보기 영역,       (z = z² + c)   320x240x8 bit x2   (2배 확대, 팔레트,
          픽셀 스케줄러,                                       렌더 시간 / fps)
          렌더 시간)  ── 토글 핸드셰이크 ──────────────────────►
```

## 버전 관리
버전마다 바뀌는 것은 **엔진** (픽셀 스케줄러 + 코어) 뿐이고 나머지는 공통이다. `V=` 로 골라서 빌드한다.

```
rtl/common/   mandel_render (보기 영역, 자동 데모, 렌더 시간, 버퍼 교체), mandel_display, mandel_system,
              palette_rom, video_timing, dpram, tmds_*
rtl/vN/       mandel_engine.v (+ 코어 등) 와 config.mk (CORE_DIV, W, IW)
```
- 엔진 인터페이스 (모든 버전 공통): `start` 펄스에 `x0 / top / step / max_iter` 를 받아 프레임 하나를 계산하고,
  `fb_we / fb_addr (픽셀 번호) / fb_data` 로 결과를 쓴 뒤 `done` 펄스. 쓰는 순서는 버전마다 달라도 된다
- 빌드 결과도 버전마다 따로: `sim/verilator/obj_vN/`, `fpga/atlys/build/vN/`
- 화면 둘째 줄 왼쪽에 버전 (`v1`) 이 표시된다
- 버전이 완성되면 git 태그 `mandel-vN`
- 새 버전 추가: `cp -r rtl/v1 rtl/v2` 후 `rtl/v2/` 만 고치고 `config.mk` 의 CORE_DIV 를 맞춘다
- 버전 폴더에 공통 파일과 **같은 이름의 파일**이 있으면 그 버전에서는 그 파일을 쓴다 (v5 는 mandel_render /
  mandel_system / mandel_display 를 바꿨다). `rtl/vN/sim/` 은 시뮬레이션에만 쓰는 파일
- `config.mk` 로 바꿀 수 있는 것: CORE_DIV, W, IW, PAR (모델 뷰어용), FB_W / FB_H / PIX_DIV / FRAME_CLKS
  (C++ 모델과 가상 모니터용), SIM_TOP (Verilator 최상위), BOARD_TOP / BOARD_UCF / BOARD_SRC (FPGA 최상위와 제약)

## 실행
```bash
cd sim/verilator
make run            # V=1 가상 모니터 (M 자동/수동, B 더블/단일 버퍼, 수동: 화살표 이동 Z 확대 X 축소, 1~4 max_iter)
make V=2 run        # 다른 버전
make check          # 첫 프레임을 C++ 고정소수점 모델과 비트 단위 비교 + 렌더 시간 / 반복 속도 보고
make check-all      # 모든 버전 검사 + 결과 요약 (RESULT 줄)
make W=24 check     # 비트 폭을 바꿔 검사 (RTL 파라미터와 모델 둘 다, obj_v1_w24/ 에 빌드)
make V=4 CORE_DIV=6 check   # clk_core 를 바꿔 검사 (obj_v4_div6/ 에 빌드, 렌더 시간이 그 클럭 기준)
make V=4 check CHECK_ARGS="--sw-iter 0"   # 검사는 기본 max_iter 255 (버전끼리 비교용). v4 의 1023 로 검사

cd sim/model        # C++ 모델만 실시간으로 (RTL 시뮬레이션 없이, CPU 멀티스레드)
make run            # V=4. FPGA 와 프레임마다 같은 그림을 FPGA 이론 속도에 맞춰 보여 준다 (P 로 속도 맞춤 끄기)
make V=1 run        # 다른 버전 (W / IW / CORE_DIV / PAR 은 rtl/vN/config.mk)

cd fpga/atlys
source ~/Xilinx/14.7/ISE_DS/settings64.sh
make V=1 && make V=1 timing && make V=1 util && make V=1 prog
make V=4 CORE_DIV=6 prog   # clk_core 를 바꿔서 빌드 (build/v4_div6/ 에 따로)
```

| 보드 입력 | 동작 |
|---|---|
| SW7 | 아래 = 자동 데모, 위 = 버튼 조작 |
| SW6 | 아래 = 더블 버퍼, 위 = 단일 버퍼 (그리는 과정이 그대로 보임) |
| BTNL / BTNR / BTNU / BTND | 4 픽셀씩 이동 (렌더 프레임마다 한 번) |
| BTNC | 1/16 확대 (SW0 올리면 축소) |
| {SW2, SW1} | max_iter = (2^IW - 1) >> {SW2, SW1}. v1~v3 (IW = 8): 255, 127, 63, 31 / v4 (IW = 10): 1023, 511, 255, 127 |
| RESET (T15) | 처음 보기 영역으로 (active-low) |

LED: 0 PLL lock, 1 RESET, 2/3 core/pix 클럭 깜빡임, 4 vsync, 5 렌더 프레임, 6 코어 busy

### Verilator 시뮬레이션과 C++ 모델 뷰어
- `sim/verilator` (`make run`) 는 RTL 을 클럭마다 계산해서 정확하지만 느리다 (v4 는 실시간의 약 2 %).
  검사 (`make check`) 와 렌더 시간 측정은 이쪽
- `sim/model` (`make run`) 은 같은 고정소수점 모델 (`sim/model/mandel_model.h`, 검사도 이 파일을 쓴다) 로 픽셀 값만
  계산한다. 보기 영역도 `mandel_render` 와 같은 순서로 갱신하므로 FPGA 와 같은 프레임이 나온다
  (v4 데모 411 번째 프레임이 RTL 시뮬레이션 화면과 픽셀 단위로 같음). 12 스레드에서 v4 의 가장 깊은 프레임이 약 16 ms
- 창 제목의 `FPGA ~ms` 는 이론값 max(반복 수 / PAR, 76800) 클럭 @ CORE_HZ (PAR = 링 수). 실제는 조금 더 걸린다
  (기본 화면에서 v3 +15 %, v4 +6 %, v1 은 픽셀당 4 클럭이 더 들어서 +9 %). 기본은 이 시간에 맞춰 프레임을 넘기므로
  애니메이션 속도가 보드와 비슷하다
- 보드의 전원 / 신호 문제 (v4 @ 166.7 MHz) 같은 것은 두 시뮬레이션 모두 보여 주지 못한다

## 고정소수점
- 코어: W = 18 비트 Q4.14 (범위 [-8, 8), 간격 2^-14). Spartan-6 DSP48A1 이 18x18 이라 곱셈 하나에 DSP 하나
- 곱셈 결과 (2W 비트) 로 탈출 판정 `zr² + zi² > 4` -> 판정에는 오버플로가 없다
- 좌표는 8 비트 더 정밀하게 (26 비트) 누적하고 코어에 넘길 때 버린다
- W = 18 이면 처음 화면 기준 약 170 배 확대부터 픽셀이 뭉개진다 (픽셀 간격 < 2^-14)
- v4 는 W = 34 (Q4.30, 간격 2^-30 ~ 1e-9), 좌표 42 비트. 같은 기준으로 약 1100 만 배까지
- 반복 횟수는 IW 비트 (v1~v3 8, v4 10). 프레임버퍼는 8 비트라서 아래 8 비트만 쓴다 (팔레트 주기 64 라 색은 같음).
  바깥 점인데 아래 8 비트가 0 (256, 512, ...) 이면 안쪽 (검정) 과 겹치므로 같은 색인 64 로 쓴다

### v2 노트
- 링: `E (곱셈기 입력) -> M (곱셈) -> A (덧셈, |z|^2) -> F (탈출 판정, 다음 z) -> E`. 단마다 다른 픽셀이 있어서
  링 전체로는 매 클럭 반복 1 회. 픽셀이 끝나면 같은 클럭에 그 자리로 새 픽셀이 들어가므로 픽셀 오버헤드도 없다
- 결과가 들어간 순서와 다르게 나오므로 픽셀 번호를 같이 들고 다닌다 (프레임버퍼는 주소로 쓰니 상관없음)
- `make V=2 DEFS=SLOTS=1 check` : 같은 하드웨어에 픽셀을 하나만 넣는 비교 실험. 파이프라인은 처리량을 올리는 기법이지
  한 개의 지연을 줄이는 기법이 아니다. z 가 직전 z 에 의존하는 반복은 서로 독립인 픽셀을 섞어 넣어야 파이프라인이 찬다
- 166.7 MHz 에서 링 안 경로는 여유가 0.7 ns 이상이고, 가장 긴 경로는 렌더러 -> 프레임버퍼 쓰기 (배선 지연).
  클럭을 더 올리려면 쓰기 주소 레지스터를 복제하거나 단을 더 넣어야 한다

### v3 노트
- 링 수에 따른 기본 화면 렌더 시간 (`make V=3 DEFS=RINGS=N check`)

  | 링 | 1 | 2 | 4 | 8 | 12 | 16 | 19 |
  |---|---|---|---|---|---|---|---|
  | ms | 21.95 | 10.98 | 5.69 | 2.83 | 1.94 | 1.51 | 1.30 |

  19 개면 이상적인 값 (21.95 / 19 = 1.16 ms) 의 89 %. 남는 차이는 픽셀 공급 / 쓰기가 클럭당 1 개라서
  반복이 적은 바깥 영역에서 링이 놀기 때문 (프레임 최소 76800 클럭 = 0.46 ms)
- 링을 붙이는 데 필요했던 것 (처음 그대로 19 개를 붙였더니 166.7 MHz 에서 -2.2 ns, 위반 경로 216 개)
  - **입출력 버퍼**: 링마다 1 칸. 바깥의 선택 회로가 링 안 경로와 같은 클럭에 엮이지 않게 한다.
    출력 버퍼가 차 있는데 또 끝나면 결과를 든 채 링을 한 바퀴 더 돈다 (주차) -> 링이 멈추지 않는다
  - **2 단계 중재**: 19 개를 한 번에 고르고 19:1 로 고르던 것을 그룹 (링 5 개) 안 -> 그룹 4 개로 나눔
  - **링 5 단**: 선택 회로 결과를 일반 레지스터 X 에 먼저 받고 곱셈기 입력 E 로 복사. 단이 늘어도 링은 단 수만큼
    픽셀을 담으므로 처리량은 그대로 (5 픽셀 인터리브)
  - **SRL 끄기**: 단마다 옮기는 cr / ci / n / idx 를 XST 가 SRL 로 바꾸면 셋업이 길어서 실패 -> `shreg_extract = "no"`
- 고친 뒤 임계 경로는 프레임버퍼 쓰기 주소, 그룹 중재기, 생성기 -> 입력 버퍼 방송이 모두 여유 0.05 ns 안팎으로 비슷하다.
  더 올리려면 이 셋을 다 손봐야 한다
- 자원: DSP 57 / 58, 레지스터 20 %, LUT 26 %, 슬라이스 40 %

### v4 노트
- 18 비트를 넘는 곱셈은 DSP48A1 (18 x 18) 여러 개로 쪼갠다. a = h 2^L + l (h 위 18 비트 부호 있음, l 아래 L 비트) 로 나누면
  일반 곱셈은 4 개, **제곱은 h*l 이 두 번 나와서 3 개** (`mandel_sq.v`).
  zr*zi 를 `2 zr zi = (zr + zi)^2 - zr^2 - zi^2` 로 바꿔서 반복 1 회 = 제곱 3 개 = DSP 9 개 (그냥 하면 12 개 -> 링 4 개).
  정수 연산으로 정확히 같은 값이라 C++ 모델 (zr*zi 그대로) 과 비트 단위로 같다. zr + zi 가 W + 1 비트라서 W <= 34
- 링: `X -> S (zr+zi) -> E -> M -> Q (제곱 3 개, 부분곱 합치기) -> A (|z|^2, re) -> B (im, 탈출 판정) -> F -> X`, 8 픽셀 인터리브.
  70 비트 가까운 덧셈이 이어지므로 v3 의 A 단을 A / B 로 나눴다. 그래도 임계 경로는 v3 와 같은 곳 (프레임버퍼 쓰기 주소, X 단 선택)
- 링 6 개 x 1 반복 / 클럭. 기본 화면 4.45 ms @ 142.9 MHz (166.7 MHz 면 3.81 ms, 이상적인 값 3.66 ms 의 96 %)
- **166.7 MHz 에서는 보드에서 HDMI 신호가 안 나온다.** 타이밍은 맞고 (5.97 ns / 6 ns) 시뮬레이션도 맞는데,
  링 1 / 3 / 4 / 5 개 (166.7 MHz) 와 링 6 개 @ 142.9 MHz 는 모두 정상 -> 링 6 개가 166.7 MHz 로 다 돌 때의
  전력 / 전원 노이즈로 TMDS 출력이 흔들리는 것으로 보인다. 그래서 v4 는 `CORE_DIV = 7` (142.9 MHz).
  타이밍 분석이 통과해도 보드에서 안 될 수 있다는 예. 시험은 `make V=4 CORE_DIV=6 prog` (build/v4_div6/) 이나
  `make V=4 DEFS=RINGS=5 prog`
- max_iter 1023 의 비용: 데모에서 가장 느린 곳은 가장 깊은 곳이 아니라 2~8 배 확대 구간 (메인 카디오이드와
  주기 2 원판 안쪽이 화면 대부분 -> 픽셀마다 1023 회). 깊은 곳 (2^19 배) 은 30~40 ms (142.9 MHz)
- 깊이 확대하려면 반복도 늘려야 한다: 2^19 배에서 max_iter 255 면 화면 거의 전부가 검다. 2^20 배를 넘으면 목표점 근처가
  작은 만델브로 안쪽이라 1023 으로도 대부분 검어서 확대 한계를 2^(W-15) 로 뒀다
- 자동 데모가 축소하면서 처음 중심으로 돌아가던 것을 중심 고정으로 바꿨다. 2^19 배에서 남은 거리의 1/16 씩 당기면
  첫 프레임에 화면 수천 개 거리를 튀어 카디오이드 안쪽 (전부 1023 회, 79 ms) 에 떨어진다

### v5 노트
```
 clk_core 142.9 MHz                                   DDR2 (MCB, 250 MHz)                 clk_pix 40 MHz
 엔진 ─► fb_writer ─(포트 0, 쓰기)─► 버퍼 0 / 1 (각 512 KB) ─(포트 1, 읽기)─► fb_reader ─► mandel_display ─► 800x600
         줄 버퍼 16 줄                                                       줄 버퍼 2 줄      팔레트, 글자
```
- **DDR2 컨트롤러**: Spartan-6 의 MCB 를 MIG 3.92 로 만들었다 (`fpga/atlys/mig/`, 생성 설정 `mig/mig.prj`.
  coregen 명령행 `coregen -b mig_ddr2.xco` 로 생성. Atlys 설정은 PoC 라이브러리의 mig_Atlys_1x128 을 참고).
  32 비트 포트 2 개: 포트 0 = 쓰기 (clk_core), 포트 1 = 읽기 (clk_pix). DDR2 300 MHz.
  클럭: MIG 의 PLL (보드 100 MHz -> VCO 600 MHz) 이 MCB 클럭과 사용자 클럭 100 MHz 를 만들고, 그 100 MHz 를 받는
  두 번째 PLL (VCO 1000 MHz) 이 TMDS 200, 픽셀 40, 연산 142.9 MHz 를 만든다. 나머지는 DDR2 보정이 끝날 때까지 리셋
- 디버그용으로 화면 셋째 줄 (렌더러 상태, 쓰기 상태, 쓰는 줄, MCB 플래그), LED6 (BUFPLL_MCB 잠금),
  LED7 (보정 완료) 을 남겨 두었다
- **쓰기 (fb_writer)**: 엔진 결과는 픽셀 번호가 뒤섞여 나오므로 칩 안 줄 버퍼 16 줄에 모은다. 가장 오래된 줄이
  800 픽셀 다 차면 40 워드 버스트 5 번으로 DDR2 에 쓴다. 엔진 생성기는 `pix_limit` (가장 오래된 줄 + 16 줄) 앞까지만
  픽셀을 만들어서 줄 버퍼가 넘칠 수 없다 (쓰기 쪽을 멈추는 장치 없이). 줄 번호는 `(off * 5243) >> 22` (DSP 1 개)
- **읽기 (fb_reader)**: 화면이 줄 y 를 내보내기 시작할 때 줄 y+1 을 DDR2 에서 50 워드 버스트 4 번으로 읽어
  줄 버퍼 다른 반쪽에 채운다 (한 줄 26 us 안에)
- 렌더러는 엔진이 끝나도 DDR2 쓰기가 끝날 때 (`fb_flushed`) 까지 기다린 뒤 버퍼를 바꾼다
- **시뮬레이션**: MCB 는 Verilator 로 못 돌려서 사용자 포트 동작 모델 (`rtl/v5/sim/mcb_model.v`) 을 붙인다. 명령보다
  데이터가 먼저 있어야 하는 규칙, FIFO 넘침 등을 어기면 오류. `make check` 는 엔진 출력과 함께 **모니터가 받은
  화면 전체**도 모델 + 팔레트와 비교한다 (DDR2 쓰기 -> 읽기 -> 화면 경로 확인, v1~v4 도 같이)
- 처음 만든 뒤 고친 것
  - 생성 한계를 생성기 진행 (`take`) 에만 넣고 링 입력 (`in_valid`) 에는 안 넣어서, 한계에 닿으면 같은 픽셀이 계속 링에
    들어갔다. 수동 모드 검사는 한계에 안 닿아서 통과했고 자동 모드에서 멈춰서 찾았다
  - 상수 곱 (step * 400) 을 LUT 로 하려고 렌더러 모듈에 `use_dsp48 = "no"` 를 붙였더니 아래 엔진까지 적용돼서
    곱셈 54 개가 전부 LUT 로 바뀌어 칩에 안 들어갔다 -> 시프트 + 덧셈으로
- **링 수 2 개 (보드 전원 한계)**: 링 6 개로는 계산이 돌기 시작하면 DDR2 보정 (calib_done) 이 풀렸다.
  시뮬레이션과 타이밍은 통과. 보드에서 차례로 확인한 것:
  - MIG 예제 설계 (`fpga/atlys/ddr_test`) 정상 -> DDR2 칩 / 핀 / MIG 설정은 문제없음
  - `DEFS=DDRONLY` (만델브로 쪽 없이 MIG 만) 정상, `DEFS=RSTBTN` (리셋 연결만 예제처럼) 실패
  - 보정이 끝날 때까지 나머지를 리셋 / `DEFS=PLLWAIT` (두 번째 PLL 정지) 해도 실패 -> 보정 뒤 계산이 시작되면 풀림
  - `DEFS=RINGS=1`, `RINGS=2` 정상, `RINGS=3`, `RINGS=4` 실패. 어댑터는 5 V 10 A 라 보드 안 1.2 V 쪽 한계로 본다
    (v4 가 166.7 MHz 에서 HDMI 가 끊긴 것과 같은 원인)
- 렌더 시간 (링 2 개): 반복 255 처음 화면 80.48 ms (링 6 개면 28.12 ms). 2~8 배 확대 구간 (안쪽이 많음) 은 1 초 넘게
  걸린다 -> 같은 전력으로 일을 줄이는 주기 검출이 다음으로 가장 필요하다
- 임계 경로: clk_core 6.892 / 7 ns, TMDS 200 MHz 4.54 / 5 ns

## 다음 단계 아이디어
- **링당 DSP 줄이기**: zr^2 - zi^2 = (zr + zi)(zr - zi) 로 바꾸면 |z|^2 에 zr^2, zi^2 가 따로 필요해서 그대로 3 개.
  대신 곱셈 하나를 LUT 곱셈기로 돌리면 링 수를 늘릴 수 있다 (LUT 는 74 % 남음)
- **쓰기 2 배**: 프레임버퍼를 짝수 / 홀수 픽셀 두 뱅크로 나누면 클럭당 2 픽셀 쓰기 -> 바깥 영역 병목 완화
- **주기 검출**: 안쪽 점은 z 가 같은 값으로 되돌아온다. 이를 찾아 일찍 끝내면 v4 / v5 의 느린 구간 (안쪽이 많은 화면)이
  크게 빨라진다 (모델로 재 보니 2~8 배 구간이 2~4 배 빨라짐, 결과는 비트 단위로 같음)
- 더블 버퍼는 vsync 에 교체하므로 렌더가 아무리 빨라도 화면은 최대 60 fps. 그 위로는 렌더 시간 (ms) 으로 비교
